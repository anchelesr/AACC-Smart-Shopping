# Implementation status (revision 9)

Revision 8 turned the design into running code for the shopper path and for the energy-adaptive control loop. **Revision 9** (final project) makes it deployable and operable: three process roles, a container image, Kubernetes manifests for a two-pool cluster, a real node-taint adapter, Prometheus metrics with alert rules and a Grafana dashboard, a CI/CD pipeline, estimated energy and carbon metrics with a reproducible experiment, an operator-controlled signal for demonstrations and a model exchange by mode. The revision 9 section after the component table says what was verified in the sandbox and, separately, what only the authors can run (a cluster, Docker registry access and GitHub were not available here). This page is the single place that says **what exists, where it is, how it was checked and where it differs from the design documents**. Where another document describes a component as a design, this page decides what is actually built. Nothing here is a measured result: all prices, energy signals and node pools are simulated, and every threshold is a demonstration value.

## How to run it

```
pip install -r requirements.txt
PYTHONPATH=src python -m shopping --demo --port 8080      # SQLite in memory, synthetic prices, operator token "demo-ops-token"
python -m pytest -q                                        # SQLite
SHOPPING_TEST_POSTGRES=postgresql://user:pw@host:5432/throwaway python -m pytest -q   # also PostgreSQL (the test schema is dropped and recreated)
```

**On a local Kubernetes cluster** (needs Docker, kind and kubectl on your machine; details in [deploy/README.md](../deploy/README.md)):

```
scripts/demo-up.sh [--with-ollama]    # builds the image, creates a kind cluster with a standard and an eco node, deploys everything
scripts/smoke.sh                      # health, metrics, then a signal change that must taint a pool and move the worker pod
scripts/demo-scenario.sh              # the scripted demonstration for the video (writes demo-evidence.txt)
scripts/demo-down.sh
```

Configuration is by environment. Database and security: `SHOPPING_DATABASE_URL`, `SHOPPING_OPS_TOKEN` (without it `/ops` and `/metrics` are disabled; `--demo` uses `demo-ops-token`). Roles and loop: `SHOPPING_ROLE` or `--role api|worker|controller|all`, `SHOPPING_INTERVAL` (seconds between control-loop steps, default 30), `SHOPPING_MODE_CACHE_SECONDS` (default 60), `SHOPPING_INITIAL_POLICY` (JSON policy of version 1), `SHOPPING_SEED_DEMO=1` (synthetic prices when the database is empty). Energy and cluster: `SHOPPING_FEED=simulated|controlled`, `SHOPPING_CLUSTER=fake|incluster|kubectl` (and `SHOPPING_K8S_API_URL`), `SHOPPING_JOB_ASSUMED_SECONDS` (assumed job length for the energy estimate). Models: `SHOPPING_LOCAL_MODEL_URL`, `SHOPPING_LOCAL_MODEL` (GREEN), `SHOPPING_LOCAL_MODEL_AMBER`, `SHOPPING_LOCAL_MODEL_TIMEOUT`, `SHOPPING_LARGE_MODEL_URL`, `SHOPPING_LARGE_MODEL_KEY`, `SHOPPING_LARGE_MODEL`. Events: `KAFKA_BOOTSTRAP`. With `--role all` the control loop (`Application.step`) runs in the server process; with separate roles the controller runs `step_control` (sense, decide, place) and the worker `step_work` (events, jobs, watch check); `POST /ops/step` runs both on demand.

### Result of the carbon experiment (simulation, estimates)

Forecast jobs run immediately against the implemented adaptive scheduler on the same simulated signal trace (14 days, 5 seeds, assumed 10 minutes per job; [full tables](carbon-experiment.md)). With the default simulator the carbon intensity at job start is **0.7 % higher** with the adaptive scheduler (no gain), because the simulator's renewable window (11:00 to 15:00) lies on the peak of its carbon intensity and "renewable forces GREEN" then releases the waiting jobs at the dirtiest time. With a coherent trace (renewable window in the trough) it is **9.5 % lower** at job start, with a longest wait of 13.2 h and no job after its deadline. The first result is a defect of the simulated data, not of the rule; it is recorded as an open decision (row 18 below). Neither number says anything about a real grid.

### Not verified

The following exist as files but **have never run**, because the sandbox had no Kubernetes cluster, no access to container registries (`python`, `postgres`, `prom/prometheus`, `grafana/grafana`, `ollama/ollama` images could not be pulled) and no GitHub Actions: the deployment on a cluster; the eviction and rescheduling of the worker pod after a taint; the RBAC rule against a real API server; the node labels set through the kind configuration; the Prometheus scrape of pods; the Grafana dashboard; the Ollama image build (the model download and the image tag `ollama/ollama:0.9.6` are unchecked); a real model answering through `ModelByMode`; the four GitHub workflows (including the push to GHCR and the deploy job); the Kafka integration tests; Electricity Maps. System pods (for example DNS) that run on the tainted pool may be evicted and restarted by the taint; the effect on the demonstration has not been observed. There is no load test (NFR-01), no availability probe (NFR-17), no measured energy (all values are estimates) and no sustainability comparison with a measured baseline (NFR-10).

## Where the code differs from the design documents

These differences are decisions taken during implementation or limits of the demonstration. **Confirmed by the authors on 25 November 2026:** the candidate model (row 3), concurrency as jobs started per tick (row 1), the stand-in local model and the in-process cache and memory (rows 6 and 7), and the single operator token (row 8). **Decisions of the authors for revision 9 (given on 25 November 2026):** Kustomize for the manifests, the Placement Controller through the Kubernetes REST API with a service account, Ollama with a small model as the real local runtime, carbon values as clearly labelled estimates (no Kepler). The other rows are recorded as they are; the authors have not yet reviewed them one by one, and rows 4 and 5 remain open work (no drift shapes, no golden set).

| # | Design says | Code does | Reason or consequence |
| --- | --- | --- | --- |
| 1 | Worker concurrency 3, 1, 1 | The limit caps the number of jobs **started per scheduler tick**; jobs run one after the other inside the application process | There are no parallel worker pods yet. Overdue jobs ignore the cap |
| 2 | Forecast workers and evaluation run as Kubernetes Jobs, the carbon controller and the scheduler as CronJobs | `--role all` runs the whole loop in one process (tests, demonstration); in the cluster the roles are separate Deployments (row 17) | Simpler to test; no Job or CronJob manifests exist |
| 3 | Forecast candidate "to be chosen during implementation" ([ADR-008](adr/ADR-008.md)) | Damped Holt linear smoothing, two parameters fitted per series | A classical method that needs no training by us; see the addendum in ADR-008 |
| 4 | Drift score with a shape (sudden, gradual, incremental, recurring) and reference windows (FR-20, V-12) | Only the live error of the candidate against the baseline and the three-strikes fallback | FR-20 is **not** implemented; `drift_checks` holds live MAE only |
| 5 | Golden set of at least 30 assistant cases (NFR-11, V-16) and a three-configuration comparison of routes (V-18) | A table-driven test of the router and tests of each guardrail; no golden set and no comparison run | Open |
| 6 | Local model runtime in the cluster | A deterministic stand-in answers when `SHOPPING_LOCAL_MODEL_URL` is not set | The stand-in only rephrases the rule result, so the output guardrail passes by construction; it says nothing about the quality of a real model |
| 7 | Answer cache and session memory "may live in the same database" | Held in process memory | Lost on restart and not shared between replicas |
| 8 | Operator endpoints "authenticated, private" | One static bearer token from the environment; no TLS, no rate limit, no user management | Demonstration level only |
| 9 | Integer identifiers and table names such as `price_observations`, `forecast_runs`, `model_evaluations`, `assistant_traces`, `review_items` | Text laptop identifiers; tables `observations`, `forecasts` (with `shadow`), `model_registry`, `traces`, `review_queue`; `forecast_runs` is kept as the small table that the pull path (`reconcile`) uses | The code follows the earlier event-bus implementation. A migration tool is not used; the schema is created on start |
| 10 | Jobs are claimed with `SELECT ... FOR UPDATE SKIP LOCKED` | A conditional `UPDATE ... WHERE status='queued'` with a lease | Works the same on SQLite and PostgreSQL |
| 11 | Energy signal simulator with a cheap and an expensive phase and random jumps | A deterministic daily wave with a seeded jitter and a renewable window of 11:00 to 15:00 UTC | Repeatable tests; the real jumps of the market are not modelled |
| 12 | Observability with Prometheus, Grafana and OpenTelemetry | `/metrics` in the Prometheus format (operator token required), Prometheus and Grafana manifests with rules and a dashboard (revision 9) | Never run on a cluster; no trace export (row 22) |
| 13 | Estimated energy of a job from the power of the worker pool | Configured 65 W (standard) and 45 W (eco) multiplied by the measured duration, or by the assumed duration (row 20) | An assumption to be calibrated, not a measurement |
| 14 | Assistant energy per token from a calibrated factor | 0.0004 Wh per token for the local model; the external model has a configured fee and no energy value | Assumptions; carbon and cost stay empty (unknown) until a first energy sample exists |
| 15 | The shopper's device identifier | Sent in the `X-Device-Id` header (the frontend uses a random UUID kept in `localStorage`) | Matches the pseudonymous design of [ADR-017](adr/ADR-017.md) |
| 16 | Router: a failed output check twice gives the template | Up to two attempts per model; the large model gets its own two attempts after the small one failed; only if all fail the template answers and the exchange is flagged | Reading of "a chosen model fails twice" |
| 17 | Forecast workers and evaluation as Kubernetes Jobs, carbon controller and scheduler as CronJobs | Three Deployments of one image (`api`, `worker`, `controller`), each running a loop; the worker Deployment is the movable workload | Simpler than Jobs and CronJobs and enough to show eviction and rescheduling; replaces the intent of row 2 for the cluster |
| 18 | Energy signal simulator with a cheap and an expensive phase | The renewable window (11:00 to 15:00) coincides with the peak of the simulated carbon intensity | Makes the adaptive scheduler look worse than immediate execution (see the experiment). **Open decision:** move the default window, or couple the intensity to the renewable flag; the experiment reports both traces until then |
| 19 | Operator can only observe signals | `ControlledFeed` and `PUT /ops/simulation` let the operator set carbon intensity, price and renewable flag | Needed to demonstrate an adaptation on demand; it is a demonstration function and must not be enabled in production (`SHOPPING_FEED=controlled` only in the kind overlay) |
| 20 | Estimated job energy from the measured duration | Optional `SHOPPING_JOB_ASSUMED_SECONDS` replaces the measured duration (600 s in the manifests) | The demonstration jobs take milliseconds; the assumed length stands for a production-size job and is labelled as an assumption wherever it is shown |
| 21 | Local model "small" for every mode | Optional `SHOPPING_LOCAL_MODEL_AMBER`: a smaller local model in AMBER (`ModelByMode`); RED never calls a model | Dynamic model exchange; the model names (`qwen2.5:1.5b`, `qwen2.5:0.5b`) are examples chosen for size and are not evaluated for answer quality |
| 22 | Observability stack with Prometheus, Grafana, OpenTelemetry | Prometheus, alert rules and Grafana are configured; there is still no OpenTelemetry or trace export, and Kepler is not used | Energy values stay estimates (decision of the authors: estimates, clearly labelled) |

See `docs/market-signals.md`. Off by default (`SHOPPING_MARKET_SCAN=on` enables it); six topics, matched in headlines (tags, description and hashtags only confirm); it does not change the forecast or the recommendation; tested without network only, never run against real feeds.

## Known limits

- The data is synthetic (`seed.py`: seeded random walks with one planned dip and one planned rise). On such data the baseline is expected to be hard to beat, and the backtest on the six laptops of the seed showed exactly that (see ADR-008). This says nothing about real prices.
- The forecast series needs 10 days of observations; shorter series produce `INSUFFICIENT_EVIDENCE` and no forecast.
- A single database connection is shared by all requests behind one lock, which is enough for the demonstration and is not a performance design.
- The simulated feed means that the demonstration changes mode with the clock; run `--demo` at different times of the day to see GREEN, AMBER and the renewable window. In the cluster demonstration the signal is set by hand (`SHOPPING_FEED=controlled`).
- The in-memory event bus does not cross process boundaries. With separate roles the worker finds new prices through the database (the pull path of `reconcile`) and the API reads the mode through its cache, so changes become visible within the interval and cache lifetime (5 s in the demonstration, 60 s by default). Kafka (`KAFKA_BOOTSTRAP`) would carry the events between processes; it is optional and not deployed by the manifests.
- PostgreSQL in the manifests is one instance without replication or backup; Prometheus keeps its data in an `emptyDir`; Grafana allows anonymous read-only access; the demonstration secrets in `overlays/kind` are public. All of this is for a throw-away cluster.
- The Ollama image runs as root (the upstream image does) and keeps both models in memory when used.
