# ADR-006 — Show forecast age instead of silently serving stale advice

**Status:** Proposed

## The problem

The scheduler may intentionally postpone a refresh, and a forecasting worker may fail. Neither case should be hidden from the shopper. We also do not want price browsing to become dependent on the current state of the model service.

## Our decision

Read the latest stored forecast, its timestamp and its status. Use it only within the defined freshness window; if it is missing or too old, show observed prices and the historical chart with a clear notice. The recommendation can fall back to historical rules with caution or return `INSUFFICIENT_EVIDENCE`.

## Options we considered

Blocking until a fresh forecast is calculated would tie page latency to background work. Silently displaying an old forecast would be faster but misleading. Showing a timestamp and a fallback is the more transparent choice.

## What this means for the project

The interface must handle several evidence states instead of only success/failure. This protects the user experience during forecast outages as long as the price database remains reachable; a complete database outage is a separate availability issue not solved by this ADR.
