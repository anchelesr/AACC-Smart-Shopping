# ADR-011 — Serving patterns: batch prediction for forecasts, model-as-a-service for the assistant

**Status:** Proposed (2026-11-25), to be confirmed by the authors

## The problem

A model can be served in different ways, and the choice decides latency, freshness, coupling and cost. The shopper path has a firm latency requirement (NFR-01), while a forecast only needs to be fresh enough. The course asks us to record the deployment and serving pattern as a decision and to state deadlines in numbers, not adjectives ("real time" is one team's "too slow").

## Our decision

**Forecast: batch prediction.** Forecasts are computed ahead of time by Jobs, stored with the model id and generation time, and looked up by laptop id (a keyed lookup). The request path never runs a model. Freshness is a soft deadline: a forecast loses value gradually, which is shown through its age, and the scheduler enforces a firm 24 h job deadline. **Assistant: model-as-a-service.** The language model is called through the gateway as an independent service, local or external, so it can be scaled, replaced and switched off by the operating mode without a release of the backend. **Not chosen: model-in-service** (the model inside the web server). The response deadline of the insights endpoint (p95 of 2 s) is firm; the assistant has its own timeout and a template fallback.

## Options we considered

- **Compute the forecast in the request (model-in-service):** always fresh but slow and unpredictable, couples releases and makes load and energy depend on traffic.
- **Stream processing of every observation:** lower latency, but a day-old price does not need it and the prices arrive in daily batches.
- **Embed the language model in the backend:** no extra network hop, but resource contention with the request path and coupled releases.
- **Other patterns from the course** (replicated, sharded, event-driven, two-phase predictions): the first two are covered by Kubernetes replicas, the others are not needed at this size.

## What this means for the project

Forecasts can be stale between runs, which is why the age is shown and the deadline exists ([ADR-006](ADR-006.md)). The extra network hop to the model is accepted for independent scaling. The two patterns are combined with a stateless serving function: the backend holds no model state.
