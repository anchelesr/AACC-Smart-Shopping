# ADR-009 — Deliver through GitHub Actions and GitOps

**Status:** Accepted (2026-11-25)

## The problem

Releases must be repeatable, checked and reversible, and AI components must not reach users without passing their quality gates. Delivery speed and safety are also architectural qualities.

## Our decision

Use GitHub Actions for pull-request checks, builds, integration tests in an ephemeral Kubernetes cluster and the AI gates (forecast backtest, assistant golden set). Build images once, tag them with the git SHA and publish them to a registry. The pipeline commits new tags to the deployment manifests, and a GitOps controller in the cluster applies them. Rollback is a revert of that commit. Only the documentation check is implemented today; the rest is the target pipeline.

## Options we considered

- **Manual kubectl apply:** not repeatable and leaves no evidence.
- **Push-based deployment from CI with cluster credentials:** puts powerful credentials in CI and does not detect drift.
- **Another CI system:** no advantage here, since the repository is on GitHub.

## What this means for the project

A controller and a manifest discipline are needed, and the ephemeral-cluster tests take time. In return, every release has a trail, rollback is simple and the AI gates run automatically. The pipeline will only become evidence after the application exists.
