# ADR-001 — Keep the API separate from batch work

**Status:** Proposed

## The problem

Opening a product page should not start a slow forecast. Even though our demonstration catalog is small, the forecasting and import tasks have different lifecycles from HTTP requests. We want to be able to change their schedule without changing the shopper interface.

## Our decision

Use one modular FastAPI application for catalog queries, discount calculations and recommendations. Run price imports and forecast refreshes in separate worker containers. Keep the modules distinct without splitting every function into its own microservice.

## Options we considered

We considered a single process for everything: it would be quicker to start, but long-running calculations could affect response times. A large microservice setup would make independent scaling possible but add too many interfaces for this project. The modular API plus separate jobs gives us the useful separation without unnecessary infrastructure.

## What this means for the project

There will be more than one workload to deploy and monitor. In return, the web API remains simpler, background jobs can be scheduled independently and model changes do not have to alter the request path.
