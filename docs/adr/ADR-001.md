# ADR-001 — Keep the API separate from batch work

**Status:** Accepted (2026-11-25)  
**Revision note:** Extended in revision 2: the backend now also hosts the Assistant Service and the LLM Gateway.

## The problem

Opening a product page should not start a slow forecast, an import or a model call that the shopper waits for. The batch and AI work have different lifecycles from HTTP requests, and we want to change their schedule without changing the shopper interface.

## Our decision

Use one modular backend for the shopper-facing functions: the Shopping API, the Assistant Service, the LLM Gateway and the policy administration entry point are modules of one deployable unit. Run price imports, carbon evaluation, forecast refreshes and model evaluation as separate scheduled workloads. Keep the modules distinct behind the interfaces of the component model, without splitting every module into its own service.

## Options we considered

- **Single process for everything:** quickest to start, but long calculations and retries could affect response times and one failure would stop everything.
- **One microservice per component:** allows independent scaling but adds many network interfaces, deployments and failure modes for a university project; the LLM Gateway in particular would need its own operations.
- **Modular backend plus separate jobs (chosen):** gives the useful separation of workloads without unnecessary infrastructure. If the gateway were shared with other applications, a separate service could be reconsidered.

## What this means for the project

There is more than one workload to deploy and monitor. In return, the request path stays simple and predictable, batch work can be scheduled and throttled independently, and model changes do not alter the request path.
