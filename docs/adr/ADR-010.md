# ADR-010 — Define components by interfaces and an allowed-to-use specification

**Status:** Accepted (2026-11-25)

## The problem

The first component diagram used unlabeled arrows, so readers could not tell whether they meant data flow or usage, and it said nothing about interfaces. The course defines architecture as components plus the usage relationships that are allowed, and expects a static model.

## Our decision

Model the components in UML 2 with provided and required interfaces and assembly connectors, use role names instead of technologies, and keep an interface catalogue and a component catalogue next to the diagram. A component may use only the interfaces it requires. Each component has one concern; the course's A and T types are not mixed; the usage graph is acyclic; models and the LLM sit behind adapters. Communication over time is shown only in the sequence diagrams.

## Options we considered

- **Boxes and arrows without interfaces:** quick to draw but ambiguous, which is what the reviewers found.
- **Package diagram by technology (frontend, backend, database):** describes deployment, not responsibilities.
- **Class-level model:** too detailed for architecture and too early.

## What this means for the project

More work up front to name and maintain interfaces. In return, replaceability (NFR-07) is checkable, a dependency check can enforce the specification in the pipeline later, and the sequences and deployment trace back to one model.

**Related requirements:** NFR-07; the course's architecture quality principles (cohesion, acyclic dependencies, models separated from business logic).
