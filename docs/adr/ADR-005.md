# ADR-005 — Use Kubernetes for distinct web and scheduled workloads

**Status:** Proposed

## The problem

The project must demonstrate a Kubernetes deployment. An always-on frontend or API and a daily importer do not need the same Kubernetes resource type, and background jobs need retry and concurrency safeguards.

## Our decision

Deploy frontend and API separately with Deployments and internal Services. Use CronJobs to start ingestion and carbon-policy checks, with a Job or worker for forecast execution. Retain PostgreSQL data on persistent storage and collect Prometheus-compatible metrics.

## Options we considered

We could run scheduled loops inside the API containers or trigger scripts manually. That would reduce initial YAML files but make lifecycle and failure handling less clear. Kubernetes adds operating overhead, yet its separation maps well to the tasks required by the course.

## What this means for the project

The configuration will include resource requests/limits, readiness and liveness checks, secrets and restricted access to metrics. `concurrencyPolicy: Forbid` is a useful guard for one CronJob, not a guarantee of exactly-once work; database-level job claims and idempotency remain necessary.

**Related requirements:** FR-08, FR-09, FR-10; NFR-08, NFR-09.
