# ADR-005 — Use Kubernetes for distinct web and scheduled workloads

**Status:** Accepted (2026-11-25)  
**Revision note:** Updated in revision 2 for the carbon controller, scheduler and mode-driven parallelism; in revision 3 for two node pools with taints, the Placement Controller, the event broker, the local model runtime, autoscaling of the backend and Kepler ([ADR-012](ADR-012.md), [ADR-013](ADR-013.md)).

## The problem

The project must demonstrate a Kubernetes deployment. An always-on frontend and backend and short scheduled jobs do not need the same resource type, and scheduled jobs need retry and concurrency safeguards. The adaptive design adds frequent small jobs and workers whose parallelism depends on the operating mode.

## Our decision

Deploy the frontend and the modular backend as separate Deployments with internal Services. Use CronJobs for the carbon controller (every 5 minutes), the job scheduler (every 15 minutes) and the daily import, and short-lived Jobs for forecast workers and the weekly model evaluation, with parallelism taken from the operating mode. Scale the backend with a horizontal pod autoscaler (CPU metrics), give every workload resource requests and limits and probes, and update by rolling update with `rollout undo` as the quick rollback. Keep PostgreSQL data on persistent storage, collect Prometheus metrics, and deliver manifests through GitOps (ADR-009).

## Options we considered

- **Scheduled loops inside the API containers:** fewer YAML files but unclear lifecycle and failure handling, and batch load would compete with requests.
- **Manual scripts:** not repeatable and no evidence of orchestration.
- **One always-on controller instead of CronJobs:** simpler loop but constant resource use for a five-minute task; the state is in the database anyway.

## What this means for the project

The configuration includes resource requests and limits, readiness and liveness checks, secrets and restricted access to metrics. `concurrencyPolicy: Forbid` guards one CronJob against overlap; it is not exactly-once. Job leases, unique keys and idempotency remain necessary.
