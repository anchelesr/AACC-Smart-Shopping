# ADR-015 — Route each assistant request by value and cost; small model locally, large model externally

**Status:** Accepted (2026-11-25), approved by the authors on the proposal of this session. The numeric limits are demonstration values.

## The problem

A model call costs tokens (output tokens are more expensive than input tokens), electricity and carbon, and a smaller local model is often good enough for routine tasks. Local models also keep data under our control and can be placed on a chosen node. LLM output is non-deterministic, so it must not sit in a safety-critical control loop. Most requests in Smart Shopping do not need a model at all, because the advice and its reasons are produced by rules. We need a defined way to decide, per request, whether a call is worth making and which model should answer.

## Our decision

The Model Router decides in four steps and records every step in the trace:

1. **Hard rules:** refused input, cache hit, insufficient evidence, provider failure or exhausted budget give REFUSED, CACHE or TEMPLATE.
2. **Value score V (0 to 4):** question type (free text or comparison 2, canned explanation 1), plus 1 if the advice carries caveats, plus 1 for a follow-up in the same session.
3. **Cost estimate per route:** estimated input and output tokens, fees for the external model, estimated energy of the local model, gCO2e from the current carbon intensity and electricity cost from the current price (signals obtained through `IOperatingMode`).
4. **Required value per route and mode:** SMALL needs V of at least 1 in GREEN and 2 in AMBER; LARGE needs V of at least 3, only in GREEN, only after the small model failed the output check, only within the per-call cost cap and the budget share reserved for it; in RED only TEMPLATE. A route whose cost estimate exceeds the cap is downgraded one step.

The small open-weight model is hosted locally (Local Model Runtime), the large model is external, preferably from a European provider; both sit behind `ILlmProvider`. Sampling temperature is 0 with fixed settings stored with the prompt version. The model receives only the evidence payload and never decides anything. A newer model or prompt runs first in shadow mode on the golden set and is then released in stages with a rollback. The daily token budget is enforced by the router (NFR-18). Whether to use an agent is decided separately in [ADR-016](ADR-016.md).

## Options we considered

- **Decide by mode and budget only (the earlier design):** simple, but it ignores how much a call is worth and what it costs now.
- **A classifier model that rates complexity:** flexible, but adds a model, tokens and a failure mode in front of every request; rejected.
- **External large model only:** simplest and strongest, but highest cost, energy and data exposure, and no placement control.
- **Local model only:** full control, but small models fail more often on free-text follow-ups, so the escalation path is kept.

## What this means for the project

The router needs a cost model with calibrated constants (tokens per request, energy per token), a golden routing set and a comparison against always-small and always-large baselines. A model runtime must be operated and placed (it is a flexible workload), and two providers mean two sets of limits to test. In return cost, energy and data exposure fall, every routing decision can be explained from its trace, and the answer path degrades to templates.
