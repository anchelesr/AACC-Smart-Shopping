# ADR-002 — Use PostgreSQL and retain where prices came from

**Status:** Proposed

## The problem

An offer is not meaningful without its retailer, timestamp, currency and exact laptop variant. Importing the same daily file twice must not create a second copy of each observation.

## Our decision

Store products, retailers, dated price observations, forecast runs and job execution records in PostgreSQL. Enforce foreign keys and a compound uniqueness constraint on observation identity, including source provenance. Use idempotent upserts during import.

## Options we considered

CSV files alone are easy to inspect but less suitable for concurrent API queries and durable job state. A document database would be flexible, yet the core relationships are known in advance and benefit from relational constraints.

## What this means for the project

Schema design and backups are additional responsibilities. The benefit is a clear audit trail for each price and more reliable repeated imports. PostgreSQL on a persistent volume is acceptable for the classroom demonstration; a managed database would be preferable for a serious production service.

**Related requirements:** FR-03, FR-04, FR-08; NFR-05.
