# ADR-012 — Notify components of changes through a publish-subscribe event bus

**Status:** Accepted (2026-11-25), on the authors' request to make Kafka functional. Implemented in `src/events` and `deploy/kafka`; see [event-bus.md](../event-bus.md) for what is verified.

## The problem

Several components must react to the same changes: new prices should trigger forecast jobs, and a mode change must reach the scheduler, the assistant gateway and the placement controller. Pure polling gives each consumer its own delay and loop; direct calls make the producer know all consumers. The course recommends combining microservices with publish-subscribe for projects like this one, and its exercises used Kafka with consumer groups on Kubernetes.

## Our decision

Introduce an event bus with three topics: `price.changed` (published by the Price Importer, consumed by the Job Scheduler) and `mode.changed` (published by the Policy Engine, consumed by the Job Scheduler, the LLM Gateway and the Placement Controller) and `events.dead` (events that failed after three attempts). Events are small notifications with at-least-once delivery; consumers are idempotent. The **database remains the source of truth**: the mode and the jobs are rows, and consumers still pull the mode (cached up to 60 s) on start and periodically, so a lost or duplicated event cannot corrupt state. We propose Kafka in KRaft mode with one broker for the demonstration (no high-availability claim), with each topic having at least as many partitions as consumer replicas, because within one consumer group each partition goes to one consumer and extra replicas stay idle.

## Options we considered

- **Polling only (revision 2):** simplest, but each consumer has its own delay and wastes calls; no decoupling of the importer from job creation.
- **Direct calls between components:** producers need to know every consumer; the allowed-to-use rules would grow.
- **A lighter broker (NATS):** less memory and simpler; a valid alternative if Kafka proves too heavy for the demonstration cluster.
- **RabbitMQ or a full ESB:** more than two low-volume topics need.
- **Database notifications (LISTEN/NOTIFY) or a job table only:** no new component, but couples consumers to the database and does not mirror the course technology.

## What this means for the project

One more component to deploy, secure, monitor (consumer lag) and test, and a risk of duplicates and reordering that consumers must tolerate. In return the importer no longer creates jobs itself, reactions are quicker than the 60 s pull, and the design shows the architectural style the course emphasises. The broker is not part of the shopper read path, so its failure degrades reaction time only (the pull remains).

Settings, failure cases and tests are in [event-bus.md](../event-bus.md): `acks=all` with an idempotent producer, manual commit after handling, idempotent handlers, a processed-events table, retry and dead letter, keys that keep per-laptop order, one partition for mode changes. NATS stays a valid fallback if Kafka proves too heavy.
