# ADR-003 — Keep forecasting behind a replaceable adapter

**Status:** Accepted (2026-11-25)  
**Revision note:** Model selection and evaluation moved to ADR-008.

## The problem

A forecast is useful only if we can explain when it was produced and by which model. The course emphasis is on architecture and the integration of existing models, not on training a new one. We also want to avoid waiting for predictions during an HTTP request.

## Our decision

Wrap every forecasting method behind one small interface (`IForecastModel`) implemented by the Forecast Model Adapter. Generate seven-day forecasts in background jobs and store the result with model identifier and creation time. Keep the advice rules separate from the forecasting component. Which models are used and when a candidate replaces the baseline is decided in ADR-008.

## Options we considered

- **Hard-wired model:** simplest initially but hard to replace or evaluate.
- **Train a bespoke neural network:** outside the course scope and the data is too small to justify it.
- **Compute on demand in the request:** makes response time depend on the model and removes the chance to schedule the calculation.

## What this means for the project

The adapter makes testing, comparison and replacement easier, but it does not make forecasts accurate. We still need to examine data coverage and uncertainty and show an explicit fallback when no trustworthy forecast exists (ADR-006).

**Related requirements:** FR-03, FR-15; NFR-01, NFR-04, NFR-07.
