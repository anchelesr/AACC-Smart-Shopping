# ADR-003 — Keep forecasting behind a replaceable adapter

**Status:** Proposed

## The problem

A forecast is useful only if we can explain when it was produced and what data it used. The course emphasis is on architecture and integration of existing models, rather than training a new one. We also want to avoid waiting for prediction calculations during an HTTP request.

## Our decision

Wrap an existing forecasting implementation or a non-trained baseline behind a small interface. Generate seven-day forecasts in the background, then store the result with model identifier and creation timestamp. Separate the recommendation rules from the forecasting component.

## Options we considered

We considered training a bespoke neural network and computing forecasts on demand. Both would add work outside the main learning objective and make response time less predictable. A fixed, hard-wired model would be simpler initially but harder to replace or evaluate.

## What this means for the project

An adapter makes testing and model comparison easier, but it does not make forecasts accurate by itself. We still need to examine data coverage and uncertainty, and we must show an explicit fallback when no trustworthy forecast is available.
